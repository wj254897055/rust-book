第 15 章

智能指针

用 Box、Rc 和 RefCell 管理堆上的数据，理解 Deref、Drop、内部可变性与引用循环。

指针（pointer）是一个通用概念，指包含内存地址的变量。这个地址指向（points at）其他数据。Rust 中最常见的指针是引用（reference），你在第 4 章已经学过。引用用 & 符号表示，并借用它们指向的值。除了引用数据之外，它们没有任何特殊能力，也没有额外开销。

另一方面，智能指针（smart pointer）是行为类似指针、但还带有额外元数据和能力的数据结构。智能指针的概念并非 Rust 独有：它起源于 C++，也存在于其他语言中。Rust 标准库定义了许多智能指针，提供引用之外的功能。为了探索这一通用概念，我们会看几个不同的智能指针示例，包括一种引用计数（reference counting）智能指针。这种指针通过记录所有者的数量，让数据可以拥有多个所有者，并在没有所有者时清理数据。

在 Rust 中，由于所有权和借用概念，引用与智能指针之间还有一个额外区别：引用只借用数据，而在许多情况下，智能指针拥有它们指向的数据。

智能指针通常用结构体实现。与普通结构体不同，智能指针实现了 Deref 和 Drop trait。Deref trait 允许智能指针结构体的实例像引用一样工作，这样你可以编写既能处理引用、又能处理智能指针的代码。Drop trait 允许你自定义智能指针实例离开作用域时运行的代码。本章会讨论这两个 trait，并说明它们为何对智能指针很重要。

鉴于智能指针模式是 Rust 中经常使用的一种通用设计模式，本章不会涵盖所有已有的智能指针。许多库有自己的智能指针，你甚至可以编写自己的。我们将介绍标准库中最常见的智能指针：

  • Box<T>，用于在堆上分配值
  • Rc<T>，一种引用计数类型，支持多重所有权
  • Ref<T> 和 RefMut<T>，通过 RefCell<T> 访问；RefCell<T> 在运行时而不是编译时强制执行借用规则

此外，我们还会介绍内部可变性（interior mutability）模式：不可变类型对外暴露用于修改内部值的 API。我们还会讨论引用循环：它们如何泄漏内存，以及如何防止。

让我们开始吧！

15.1使用 Box<T> 指向堆上的数据

最直接的智能指针是盒子（box），其类型写作 Box<T>。盒子允许你把数据存储在堆上而不是栈上。留在栈上的是指向堆数据的指针。关于栈与堆的区别，请回顾第 4 章。

盒子除了把数据存储在堆上而不是栈上之外，没有性能开销。但它们也没有太多额外能力。你通常会在以下情况使用它们：

  • 当你有一个在编译时无法确定大小的类型，而又想在一个要求确切大小的上下文中使用该类型的值时
  • 当你有大量数据，想转移所有权，同时确保数据在转移时不会被复制时
  • 当你想拥有一个值，并且只关心它的类型实现了某个特定 trait，而不关心具体类型时

我们会在“用盒子实现递归类型”中演示第一种情况。第二种情况下，转移大量数据的所有权可能耗时很久，因为数据会在栈上被复制来复制去。为了提升性能，我们可以把大量数据存放在堆上的盒子里。这样，只有少量指针数据会在栈上复制，而它引用的数据会留在堆上的同一个位置。第三种情况称为 trait 对象（trait object），第 18 章的“使用 Trait 对象抽象共享行为”专门讨论这个主题。所以你在这里学到的内容，之后还会再次用到！

在堆上存储数据

在讨论 Box<T> 的堆存储用例之前，我们先介绍语法，以及如何与存储在 Box<T> 中的值交互。

代码清单 15-1 展示了如何使用盒子把 i32 值存储在堆上。

文件名：src/main.rs

fn main() {
    let b = Box::new(5);
    println!("b = {b}");
}

代码清单 15-1：使用盒子在堆上存储一个 i32 值

我们定义变量 b，其值是一个指向堆上分配的 5 的 Box。这个程序会打印 b = 5；在这种情况下，访问盒子中数据的方式，与数据在栈上时类似。和任何拥有所有权的值一样，当盒子离开作用域时——比如 b 在 main 结束时——它会被释放。释放同时发生在盒子上（存储在栈上）和它指向的数据上（存储在堆上）。

把单个值放到堆上并不太有用，所以你不会经常以这种方式单独使用盒子。在大多数情况下，把像单个 i32 这样的值放在默认存储位置——栈上——更合适。接下来看一个例子：盒子让我们能够定义原本无法定义的类型。

用盒子实现递归类型

递归类型（recursive type）的值可以把同类型的另一个值作为自身的一部分。递归类型会带来一个问题：Rust 需要在编译时知道一个类型占用多少空间。然而，递归类型值的嵌套理论上可以无限继续，因此 Rust 无法知道该值需要多少空间。由于盒子具有已知大小，我们可以通过在递归类型定义中插入盒子，来启用递归类型。

作为递归类型的例子，我们来探索 cons 列表。这是函数式编程语言中常见的数据类型。我们要定义的 cons 列表类型除了递归之外很直接；因此，当你遇到涉及递归类型的更复杂情况时，这个例子中的概念会很有用。

理解 cons 列表

cons 列表（cons list）是一种来自 Lisp 编程语言及其方言的数据结构，由嵌套的序对组成，是 Lisp 版本的链表。它的名字来自 Lisp 中的 cons 函数（construct function 的缩写），该函数用两个参数构造一个新的序对。对一个由某个值和另一个序对组成的序对调用 cons，就能构造出由递归序对组成的 cons 列表。

例如，下面是包含列表 1, 2, 3 的 cons 列表的伪代码表示，每个序对都在括号中：

(1, (2, (3, Nil)))

cons 列表中的每一项包含两个元素：当前项的值和下一项。列表中的最后一项只包含一个名为 Nil 的值，没有下一项。cons 列表通过递归调用 cons 函数产生。表示递归基准情况的标准名称是 Nil。注意，这与第 6 章讨论的“null”或“nil”概念不同；后者表示无效或不存在的值。

cons 列表在 Rust 中并不是一种常用的数据结构。在 Rust 中，大多数时候如果你有一个项目列表，Vec<T> 是更好的选择。其他更复杂的递归数据类型确实在各种场景中有用，但本章从 cons 列表开始，可以让我们在不受太多干扰的情况下探索盒子如何帮助我们定义递归数据类型。

代码清单 15-2 包含 cons 列表的枚举定义。注意，这段代码还不能编译，因为 List 类型没有已知大小，我们稍后会演示这一点。

文件名：src/main.rs

enum List {
    Cons(i32, List),
    Nil,
}

fn main() {}

代码清单 15-2：第一次尝试定义一个枚举，表示保存 i32 值的 cons 列表数据结构

注意：为了这个例子，我们实现的 cons 列表只保存 i32 值。我们也可以像第 10 章讨论的那样使用泛型，定义一个可以存储任意类型值的 cons 列表类型。

使用 List 类型存储列表 1, 2, 3 的代码如代码清单 15-3 所示。

文件名：src/main.rs

enum List {
    Cons(i32, List),
    Nil,
}

// --snip--

use crate::List::{Cons, Nil};

fn main() {
    let list = Cons(1, Cons(2, Cons(3, Nil)));
}

代码清单 15-3：使用 List 枚举存储列表 1, 2, 3

第一个 Cons 值保存 1 和另一个 List 值。这个 List 值是另一个 Cons 值，保存 2 和另一个 List 值。这个 List 值又是另一个 Cons 值，保存 3 和一个 List 值，最后这个 List 值是 Nil——表示列表结束的非递归变体。

代码清单 15-4：尝试定义递归枚举时得到的错误

错误显示这个类型“具有无限大小”。原因是我们定义 List 时使用了一个递归变体：它直接保存自身的另一个值。因此，Rust 无法确定存储一个 List 值需要多少空间。我们来分析为什么会得到这个错误。首先看看 Rust 如何决定存储一个非递归类型的值需要多少空间。

计算非递归类型的大小

回顾第 6 章讨论枚举定义时，代码清单 6-2 中定义的 Message 枚举：

enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    ChangeColor(i32, i32, i32),
}

fn main() {}

为了确定给一个 Message 值分配多少空间，Rust 会遍历每个变体，找出需要空间最大的变体。Rust 发现 Message::Quit 不需要任何空间，Message::Move 需要足够存储两个 i32 值的空间，等等。因为只会使用一个变体，所以一个 Message 值最多需要的空间，就是存储它最大变体所需的空间。

将此与 Rust 尝试确定代码清单 15-2 中 List 枚举这类递归类型需要多少空间时发生的情况进行对比。编译器首先查看 Cons 变体，它保存一个 i32 类型的值和一个 List 类型的值。因此，Cons 需要的空间等于一个 i32 的大小加上一个 List 的大小。为了计算 List 类型需要多少内存，编译器又查看各个变体，从 Cons 开始。Cons 变体保存一个 i32 值和一个 List 值，这个过程会无限继续，如图 15-1 所示。

得到已知大小的递归类型

因为 Rust 无法确定递归定义的类型需要分配多少空间，编译器会给出错误，并提供有用的建议：

help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
2 |     Cons(i32, Box<List>),
  |               ++++    +

在这个建议中，间接（indirection）的意思是：不要直接存储值，而应改为通过存储指向值的指针来间接存储值。

因为 Box<T> 是一个指针，Rust 总是知道 Box<T> 需要多少空间：指针的大小不会随它指向的数据量而变化。这意味着我们可以在 Cons 变体中放入 Box<T>，而不是直接放入另一个 List 值。Box<T> 会指向下一个 List 值，而这个值位于堆上，而不是位于 Cons 变体内部。从概念上讲，我们仍然有一个列表，由保存其他列表的列表构成，但这种实现更像是把项目彼此相邻放置，而不是相互嵌套。

我们可以把代码清单 15-2 中 List 枚举的定义以及代码清单 15-3 中对 List 的使用，改成代码清单 15-5 中的代码，这样就可以编译了。

文件名：src/main.rs

enum List {
    Cons(i32, Box<List>),
    Nil,
}

use crate::List::{Cons, Nil};

fn main() {
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
}

代码清单 15-5：使用 Box<T> 以获得已知大小的 List 定义

Cons 变体需要一个 i32 的大小，加上存储盒子指针数据的空间。Nil 变体不存储任何值，所以它在栈上需要的空间比 Cons 变体少。现在我们知道，任何 List 值都会占用一个 i32 的大小加上一个盒子指针数据的大小。通过使用盒子，我们打破了无限的递归链，因此编译器可以算出存储一个 List 值所需的大小。图 15-2 展示了 Cons 变体现在的样子。

盒子只提供间接和堆分配；它们没有其他特殊能力，比如我们将在其他智能指针类型中看到的能力。它们也不会带来这些特殊能力所需的性能开销，因此在 cons 列表这样只需要间接的场景中很有用。我们会在第 18 章看到更多盒子的用例。

Box<T> 类型之所以是智能指针，是因为它实现了 Deref trait，这使得 Box<T> 值可以像引用一样使用。当 Box<T> 值离开作用域时，盒子指向的堆数据也会因为 Drop trait 的实现而被清理。这两个 trait 对于本章其余部分讨论的其他智能指针类型所提供的功能甚至更重要。让我们更详细地探索这两个 trait。

15.2将智能指针当作常规引用：Deref Trait

实现 Deref trait 可以让你自定义解引用运算符（dereference operator）* 的行为（不要与乘法运算符或通配符运算符混淆）。通过以实现 Deref 的方式让智能指针可以像常规引用一样使用，你可以编写操作引用的代码，并把同样的代码用于智能指针。

我们先看看解引用运算符如何与常规引用配合工作。然后，我们尝试定义一个行为类似 Box<T> 的自定义类型，并看看为什么解引用运算符不能像对待引用那样对待我们新定义的类型。我们会探索实现 Deref trait 如何让智能指针能够以类似引用的方式工作。接着，我们会了解 Rust 的解引用强制转换（deref coercion）特性，以及它如何让我们既能处理引用，也能处理智能指针。

沿着引用找到值

常规引用是一种指针。可以把指针想象成指向存储在别处的值的箭头。代码清单 15-6 中，我们创建了一个指向 i32 值的引用，然后使用解引用运算符沿着引用找到该值。

文件名：src/main.rs

fn main() {
    let x = 5;
    let y = &x;

    assert_eq!(5, x);
    assert_eq!(5, *y);
}

代码清单 15-6：使用解引用运算符沿着引用找到 i32 值

变量 x 保存一个 i32 值 5。我们把 y 设为指向 x 的引用。我们可以断言 x 等于 5。然而，如果我们要对 y 中的值做断言，就必须使用 *y 沿着引用找到它指向的值（也就是解引用），这样编译器才能比较实际的值。一旦解引用 y，我们就能访问 y 指向的整数值，并将其与 5 比较。

像引用一样使用 Box<T>

我们可以重写代码清单 15-6 中的代码，改用 Box<T> 而不是引用；代码清单 15-7 中对 Box<T> 使用解引用运算符的方式，与代码清单 15-6 中对引用使用解引用运算符的方式相同。

fn main() {

代码清单 15-7：对 Box<i32> 使用解引用运算符

代码清单 15-7 与 15-6 的主要区别在于，这里我们把 y 设为一个盒子的实例，它指向 x 的一个副本，而不是指向 x 值的引用。在最后一个断言中，我们可以使用解引用运算符沿着盒子的指针找到值，就像 y 是引用时一样。接下来，我们通过定义自己的盒子类型，来探索 Box<T> 究竟有什么特殊之处，使我们能够使用解引用运算符。

定义自己的智能指针

我们来构建一个类似标准库 Box<T> 的包装类型，体验智能指针类型默认情况下与引用有什么不同。然后，我们看看如何添加使用解引用运算符的能力。

注意：我们即将构建的 MyBox<T> 类型与真正的 Box<T> 有一个重要区别：我们的版本不会把数据存储在堆上。这个例子聚焦于 Deref，所以数据实际存储在哪里，不如指针式行为重要。

Box<T> 类型最终定义为只有一个元素的元组结构体，因此代码清单 15-8 以同样的方式定义了 MyBox<T> 类型。我们还会定义一个 new 函数，与 Box<T> 上定义的 new 函数对应。

文件名：src/main.rs

struct MyBox<T>(T);

impl<T> MyBox<T> {
    fn new(x: T) -> MyBox<T> {
        MyBox(x)
    }
}

fn main() {}

代码清单 15-8：定义 MyBox<T> 类型

我们定义了一个名为 MyBox 的结构体，并声明泛型参数 T，因为我们希望这个类型能保存任意类型的值。MyBox 是一个元组结构体，只有一个 T 类型的元素。MyBox::new 函数接收一个 T 类型的参数，并返回一个保存传入值的 MyBox 实例。

我们把代码清单 15-7 中的 main 函数加到代码清单 15-8 中，并改为使用我们定义的 MyBox<T> 类型，而不是 Box<T>。代码清单 15-9 中的代码无法编译，因为 Rust 不知道如何解引用 MyBox。

文件名：src/main.rs

struct MyBox<T>(T);

    }
}

fn main() {

    let y = MyBox::new(x);

    assert_eq!(5, x);
    assert_eq!(5, *y);
}

实现 Deref Trait

如第 10 章“在类型上实现 Trait”所述，要实现一个 trait，我们需要为 trait 的必需方法提供实现。标准库提供的 Deref trait 要求我们实现一个名为 deref 的方法，它借用 self 并返回指向内部数据的引用。代码清单 15-10 包含为 MyBox<T> 定义添加的 Deref 实现。

文件名：src/main.rs

use std::ops::Deref;

impl<T> Deref for MyBox<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &self.0
    }
}

struct MyBox<T>(T);

impl<T> MyBox<T> {
    fn new(x: T) -> MyBox<T> {
        MyBox(x)
    }
}

fn main() {
    let x = 5;
    let y = MyBox::new(x);

    assert_eq!(5, x);
    assert_eq!(5, *y);
}

代码清单 15-10：在 MyBox<T> 上实现 Deref

type Target = T; 语法为 Deref trait 定义了一个关联类型。关联类型是声明泛型参数的一种略有不同的方式，但现在不必担心；我们会在第 20 章更详细地介绍。

我们在 deref 方法体中填入 &self.0，让 deref 返回一个引用，指向我们想通过 * 运算符访问的值；回顾第 5 章“用元组结构体创建不同类型”可知，.0 访问元组结构体中的第一个值。代码清单 15-9 中对 MyBox<T> 值调用 * 的 main 函数现在可以编译，断言也能通过！

没有 Deref trait 时，编译器只能解引用 & 引用。deref 方法让编译器能够接受任何实现了 Deref 的类型的值，并调用 deref 方法获得一个它知道如何解引用的引用。

当我们在代码清单 15-9 中输入 *y 时，Rust 在幕后实际运行的是这段代码：

*(y.deref())

Rust 会把 * 运算符替换为对 deref 方法的调用，然后进行一次普通解引用，这样我们就不必考虑是否需要调用 deref 方法。这个 Rust 特性让我们编写的代码无论面对常规引用还是实现了 Deref 的类型，都能以相同方式工作。

deref 方法返回值的引用，以及 *(y.deref()) 括号外仍然需要普通解引用，原因与所有权系统有关。如果 deref 方法直接返回值而不是值的引用，值就会从 self 中移出。在这种情况下，以及在大多数使用解引用运算符的情况下，我们不想获取 MyBox<T> 内部值的所有权。

注意，每次在代码中使用 * 时，* 运算符只会被替换为一次 deref 方法调用，然后再调用一次 * 运算符。因为 * 运算符的替换不会无限递归，最终得到的是 i32 类型的数据，与代码清单 15-9 中 assert_eq! 里的 5 匹配。

在函数和方法中使用解引用强制转换

解引用强制转换（deref coercion）会把指向实现了 Deref trait 的类型的引用，转换为指向另一种类型的引用。例如，解引用强制转换可以把 &String 转换为 &str，因为 String 实现了 Deref trait，其 deref 返回 &str。解引用强制转换是 Rust 对函数和方法参数执行的一种便利转换，并且只对实现了 Deref trait 的类型生效。当我们把指向某个类型值的引用作为参数，传给一个参数类型不匹配的函数或方法时，它会自动发生。一系列对 deref 方法的调用会把我们提供的类型转换为参数所需的类型。

Rust 加入解引用强制转换，是为了让编写函数和方法调用的程序员不必添加那么多显式的 & 和 * 引用与解引用。解引用强制转换特性还让我们可以编写更多既能处理引用、又能处理智能指针的代码。

为了观察解引用强制转换的实际效果，我们使用代码清单 15-8 中定义的 MyBox<T> 类型，以及代码清单 15-10 中添加的 Deref 实现。代码清单 15-11 展示了一个接收字符串切片参数的函数定义。

(*m) 把 MyBox<String> 解引用为 String。然后，& 和 [..] 取得与整个字符串相等的 String 字符串切片，以匹配 hello 的签名。没有解引用强制转换时，这段代码涉及这么多符号，更难阅读、编写和理解。解引用强制转换让 Rust 自动为我们处理这些转换。

当相关类型定义了 Deref trait 时，Rust 会分析类型，并尽可能多次使用 Deref::deref，以获得与参数类型匹配的引用。需要插入 Deref::deref 的次数在编译时确定，因此使用解引用强制转换没有运行时开销！

处理可变引用上的解引用强制转换

与使用 Deref trait 覆盖不可变引用上的 * 运算符类似，你可以使用 DerefMut trait 覆盖可变引用上的 * 运算符。

Rust 在三种情况下发现类型和 trait 实现时，会执行解引用强制转换：

  1. 当 T: Deref<Target=U> 时，从 &T 转换为 &U
  2. 当 T: DerefMut<Target=U> 时，从 &mut T 转换为 &mut U
  3. 当 T: Deref<Target=U> 时，从 &mut T 转换为 &U

前两种情况相同，只是第二种实现了可变性。第一种情况说明，如果你有一个 &T，并且 T 实现了 Deref 到某个类型 U，你可以透明地得到 &U。第二种情况说明，可变引用也会发生同样的解引用强制转换。

第三种情况更棘手：Rust 也会把可变引用强制转换为不可变引用。但反过来不行：不可变引用永远不会强制转换为可变引用。由于借用规则，如果你有一个可变引用，那么这个可变引用必须是该数据的唯一引用（否则程序无法编译）。把一个可变引用转换为一个不可变引用永远不会违反借用规则。而把不可变引用转换为可变引用，需要原来的不可变引用是该数据的唯一不可变引用，但借用规则并不保证这一点。因此，Rust 不能假设可以把不可变引用转换为可变引用。

15.3用 Drop Trait 在清理时运行代码

智能指针模式中第二个重要的 trait 是 Drop，它让你自定义值即将离开作用域时发生的事情。你可以为任何类型实现 Drop trait，这段代码可用于释放文件或网络连接等资源。

我们在智能指针的语境中介绍 Drop，因为实现智能指针时几乎总会用到 Drop trait 的功能。例如，当 Box<T> 被丢弃时，它会释放盒子指向的堆空间。

在某些语言中，对于某些类型，程序员必须在每次使用完这些类型的实例后调用代码来释放内存或资源。例子包括文件句柄、套接字和锁。如果程序员忘记这样做，系统可能会过载并崩溃。在 Rust 中，你可以指定每当值离开作用域时运行某段代码，编译器会自动插入这段代码。因此，你不需要小心翼翼地在一个程序中所有使用完某个类型实例的地方都放置清理代码——你仍然不会泄漏资源！

你通过实现 Drop trait 来指定值离开作用域时要运行的代码。Drop trait 要求你实现一个名为 drop 的方法，它接收 self 的可变引用。为了观察 Rust 何时调用 drop，我们先在 drop 实现中使用 println! 语句。

15.4Rc<T>：引用计数智能指针

在大多数情况下，所有权是明确的：你清楚哪个变量拥有某个值。然而，有些情况下，一个值可能有多个所有者。例如，在图数据结构中，多条边可能指向同一个节点，而这个节点在概念上由所有指向它的边共同拥有。除非没有任何边指向该节点、因而没有所有者，否则这个节点不应被清理。

你必须使用 Rust 类型 Rc<T> 显式启用多重所有权，它是引用计数（reference counting）的缩写。Rc<T> 类型记录指向某个值的引用数量，以判断该值是否仍在使用。如果某个值的引用数为零，就可以清理该值，而不会使任何引用失效。

可以把 Rc<T> 想象成家庭娱乐室里的电视。当一个人进来看电视时，他会打开电视。其他人也可以进入房间一起看。当最后一个人离开房间时，他会关掉电视，因为已经没人使用了。如果还有人在看时某人把电视关掉，剩下的观众肯定会抗议！

当我们想在堆上分配一些数据，供程序的多个部分读取，而又无法在编译时确定哪一部分最后使用完这些数据时，就使用 Rc<T> 类型。如果我们知道哪一部分最后结束，就可以让那一部分成为数据的所有者，编译时执行的常规所有权规则就会生效。

注意，Rc<T> 只用于单线程场景。在第 16 章讨论并发时，我们会介绍如何在多线程程序中进行引用计数。

15.5RefCell<T> 与内部可变性模式

内部可变性（interior mutability）是 Rust 中的一种设计模式，它允许你在存在指向数据的不可变引用时修改数据；通常，借用规则不允许这样做。为了修改数据，该模式在数据结构内部使用 unsafe 代码，绕过 Rust 通常管理修改和借用的规则。unsafe 代码向编译器表明，我们在手动检查规则，而不是依赖编译器替我们检查；我们会在第 20 章更详细地讨论 unsafe 代码。

只有当我们可以确保借用规则在运行时得到遵守（即使编译器无法保证）时，才能使用采用内部可变性模式的类型。涉及的 unsafe 代码随后被包装在安全的 API 中，而外部类型仍然是不可变的。

我们通过遵循内部可变性模式的 RefCell<T> 类型来探索这个概念。

在运行时强制执行借用规则

与 Rc<T> 不同，RefCell<T> 类型表示对其保存数据的单一所有权。那么，RefCell<T> 与 Box<T> 这类类型有什么不同？回顾你在第 4 章学到的借用规则：

  • 在任何给定时刻，你只能拥有一个可变引用，或者任意数量的不可变引用（但不能同时拥有两者）。
  • 引用必须始终有效。

对于引用和 Box<T>，借用规则的不变量在编译时强制执行。对于 RefCell<T>，这些不变量在运行时强制执行。使用引用时，如果违反这些规则，会得到编译器错误。使用 RefCell<T> 时，如果违反规则，程序会 panic 并退出。

在编译时检查借用规则的优点是，错误会更早地在开发过程中被发现，而且对运行时性能没有影响，因为所有分析都提前完成。因此，在大多数情况下，编译时检查借用规则是最佳选择，这也是 Rust 的默认方式。

在运行时检查借用规则的优点是，某些内存安全的场景可以被允许，而编译时检查原本会禁止它们。像 Rust 编译器这样的静态分析本质上是保守的。代码的某些属性无法通过分析代码检测出来：最著名的例子是停机问题，它超出了本书的范围，但值得研究。

因为有些分析无法完成，如果 Rust 编译器不能确定代码符合所有权规则，它可能会拒绝一个正确的程序；这就是它的保守之处。如果 Rust 接受一个错误的程序，用户就无法信任 Rust 提供的保证。然而，如果 Rust 拒绝一个正确的程序，程序员会感到不便，但不会发生灾难性的事情。当你确信代码遵守借用规则，但编译器无法理解并保证这一点时，RefCell<T> 类型就很有用。

与 Rc<T> 类似，RefCell<T> 只用于单线程场景；如果你尝试在多线程上下文中使用它，会得到编译时错误。我们会在第 16 章讨论如何在多线程程序中获得 RefCell<T> 的功能。

以下是选择 Box<T>、Rc<T> 或 RefCell<T> 的理由回顾：

  • Rc<T> 允许同一数据拥有多个所有者；Box<T> 和 RefCell<T> 只有单一所有者。
  • Box<T> 允许在编译时检查不可变或可变借用；Rc<T> 只允许在编译时检查不可变借用；RefCell<T> 允许在运行时检查不可变或可变借用。
  • 因为 RefCell<T> 允许在运行时检查可变借用，所以即使 RefCell<T> 是不可变的，你也可以修改其内部的值。

修改不可变值内部的值，就是内部可变性模式。我们来看一个内部可变性有用的场景，并研究它为什么可行。

用模拟对象进行测试

有时在测试期间，程序员会用一个类型代替另一个类型，以观察特定行为并断言其实现正确。这个占位类型称为测试替身（test double）。可以把它想象成电影制作中的替身演员：由一个人代替演员完成特别困难的场景。测试替身在我们运行测试时替代其他类型。模拟对象（mock object）是一种特定的测试替身，它记录测试期间发生的事情，以便你断言正确的操作发生了。

Rust 没有与其他语言相同意义上的对象，标准库也没有像某些其他语言那样内置模拟对象功能。不过，你完全可以创建一个结构体来充当模拟对象的角色。

我们要测试的场景是：创建一个库，跟踪某个值与最大值的关系，并根据当前值接近最大值的程度发送消息。例如，这个库可以用来跟踪用户允许进行的 API 调用次数配额。

我们的库只提供功能：跟踪值接近最大值的程度，以及在什么时候应该发送什么消息。使用我们库的应用程序需要提供发送消息的机制：应用程序可以直接向用户显示消息、发送电子邮件、发送短信，或者做其他事情。库不需要知道这些细节。它只需要一个实现了我们将提供的名为 Messenger 的 trait 的东西。代码清单 15-20 展示了库代码。

    fn send(&self, msg: &str);

}

    T: Messenger,

            messenger,
            value: 0,
            max,
        }

        }
    }
}

在运行时跟踪借用

创建不可变引用和可变引用时，我们分别使用 & 和 &mut 语法。使用 RefCell<T> 时，我们使用 borrow 和 borrow_mut 方法，它们属于 RefCell<T> 的安全 API。borrow 方法返回智能指针类型 Ref<T>，borrow_mut 返回智能指针类型 RefMut<T>。这两种类型都实现了 Deref，所以我们可以像常规引用一样使用它们。

RefCell<T> 记录当前有多少个 Ref<T> 和 RefMut<T> 智能指针处于活动状态。每次调用 borrow，RefCell<T> 都会增加活动不可变借用的计数。当 Ref<T> 值离开作用域时，不可变借用的计数减少 1。与编译时借用规则一样，RefCell<T> 允许我们在任意时刻拥有多个不可变借用或一个可变借用。

允许多个所有者拥有可变数据

RefCell<T> 的一种常见用法是与 Rc<T> 结合。回顾一下，Rc<T> 允许某些数据拥有多个所有者，但它只提供对该数据的不可变访问。如果你有一个保存 RefCell<T> 的 Rc<T>，就能得到一个既可以有多个所有者、又可以修改的值！

例如，回顾代码清单 15-18 中的 cons 列表例子，我们使用 Rc<T> 让多个列表共享对另一个列表的所有权。因为 Rc<T> 只保存不可变值，一旦创建列表，我们就不能修改其中的任何值。我们来加入 RefCell<T>，利用它修改列表中值的能力。代码清单 15-24 展示了通过在 Cons 定义中使用 RefCell<T>，我们可以修改所有列表中存储的值。

    Cons(Rc<RefCell<i32>>, Rc<List>),
    Nil,
}

use std::cell::RefCell;
use std::rc::Rc;

    let b = Cons(Rc::new(RefCell::new(3)), Rc::clone(&a));
    let c = Cons(Rc::new(RefCell::new(4)), Rc::clone(&a));

15.6引用循环会泄漏内存

Rust 的内存安全保证使意外创建永远不会被清理的内存（称为内存泄漏，memory leak）变得困难，但并非不可能。完全防止内存泄漏并不是 Rust 的保证之一，这意味着在 Rust 中内存泄漏是内存安全的。通过使用 Rc<T> 和 RefCell<T>，我们可以看到 Rust 允许内存泄漏：可以创建项目彼此循环引用的引用。这会造成内存泄漏，因为循环中每个项目的引用计数永远不会达到 0，这些值也永远不会被丢弃。

创建引用循环

我们来看引用循环可能如何发生，以及如何防止它，先从代码清单 15-25 中 List 枚举的定义和 tail 方法开始。

文件名：src/main.rs

use crate::List::{Cons, Nil};
use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
enum List {
    Cons(i32, RefCell<Rc<List>>),
    Nil,
}

impl List {
    fn tail(&self) -> Option<&RefCell<Rc<List>>> {
        match self {
            Cons(_, item) => Some(item),
            Nil => None,
        }
    }
}

与现实世界的程序相比，这个例子中创建引用循环的后果并不严重：创建引用循环后，程序马上就结束了。然而，如果更复杂的程序在循环中分配了大量内存，并长时间持有它，程序会使用超过所需的内存，可能压垮系统，导致可用内存耗尽。

创建引用循环并不容易，但也并非不可能。如果你有包含 Rc<T> 值的 RefCell<T> 值，或者类似具有内部可变性和引用计数的嵌套类型组合，就必须确保不创建循环；你不能依赖 Rust 来捕获它们。创建引用循环会是程序中的逻辑错误，你应该通过自动化测试、代码审查和其他软件开发实践来尽量减少它。

避免引用循环的另一种解决方案是重新组织数据结构，让一些引用表达所有权，而另一些不表达。这样，循环可以由一些所有权关系和一些非所有权关系组成，只有所有权关系会影响值是否可以被丢弃。在代码清单 15-25 中，我们始终希望 Cons 变体拥有其列表，所以无法重新组织数据结构。我们来看一个由父节点和子节点组成的图的例子，了解非所有权关系何时是防止引用循环的合适方式。

使用 Weak<T> 防止引用循环

到目前为止，我们已经演示了调用 Rc::clone 会增加 Rc<T> 实例的 strong_count，而 Rc<T> 实例只有在 strong_count 为 0 时才会被清理。你还可以通过调用 Rc::downgrade 并传入 Rc<T> 的引用，创建指向 Rc<T> 实例内部值的弱引用。强引用（strong reference）是你共享 Rc<T> 实例所有权的方式。弱引用（weak reference）不表达所有权关系，其计数不影响 Rc<T> 实例何时被清理。它们不会造成引用循环，因为任何涉及弱引用的循环都会在相关值的强引用计数变为 0 时被打破。

调用 Rc::downgrade 时，你会得到 Weak<T> 类型的智能指针。调用 Rc::downgrade 不会把 Rc<T> 实例中的 strong_count 增加 1，而是把 weak_count 增加 1。Rc<T> 类型使用 weak_count 记录存在多少个 Weak<T> 引用，类似于 strong_count。区别在于，Rc<T> 实例被清理时，weak_count 不必为 0。

因为 Weak<T> 引用的值可能已经被丢弃，所以要对 Weak<T> 指向的值做任何操作，你必须确保该值仍然存在。为此，可以调用 Weak<T> 实例上的 upgrade 方法，它会返回 Option<Rc<T>>。如果 Rc<T> 值尚未被丢弃，你会得到 Some；如果 Rc<T> 值已被丢弃，你会得到 None。因为 upgrade 返回 Option<Rc<T>>，Rust 会确保处理 Some 和 None 两种情况，不会出现无效指针。

举个例子，我们不再使用只了解下一项的列表，而是创建一棵树，树中的项目既了解子项，也了解父项。

创建树形数据结构

首先，我们构建一棵树，节点了解自己的子节点。我们创建一个名为 Node 的结构体，保存自己的 i32 值以及对子 Node 的引用：

use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
struct Node {
    value: i32,
    children: RefCell<Vec<Rc<Node>>>,
}

我们希望 Node 拥有其子节点，并希望与变量共享这种所有权，以便可以直接访问树中的每个 Node。为此，我们把 Vec<T> 的元素定义为 Rc<Node> 类型。我们还希望修改哪些节点是另一个节点的子节点，所以在 children 中，把 Vec<Rc<Node>> 包在 RefCell<T> 里。

接下来，我们使用这个结构体定义，创建一个名为 leaf 的 Node 实例，值为 3，没有子节点；再创建一个名为 branch 的实例，值为 5，并把 leaf 作为其子节点之一，如代码清单 15-27 所示。

use std::rc::Rc;

我们克隆 leaf 中的 Rc<Node> 并存入 branch，这意味着 leaf 中的 Node 现在有两个所有者：leaf 和 branch。我们可以通过 branch.children 从 branch 到达 leaf，但无法从 leaf 到达 branch。原因是 leaf 没有指向 branch 的引用，也不知道它们之间的关系。我们希望 leaf 知道 branch 是它的父节点。接下来我们就来做这件事。

添加从子节点到父节点的引用

为了让子节点知道自己的父节点，我们需要在 Node 结构体定义中添加一个 parent 字段。问题在于确定 parent 应该是什么类型。我们知道它不能包含 Rc<T>，因为那会造成引用循环：leaf.parent 指向 branch，而 branch.children 指向 leaf，从而导致它们的 strong_count 永远不为 0。

换个角度思考这些关系：父节点应该拥有子节点：如果父节点被丢弃，子节点也应该被丢弃。然而，子节点不应拥有父节点：如果我们丢弃子节点，父节点应该仍然存在。这正是弱引用的用武之地！

所以，我们不让 parent 使用 Rc<T>，而是使用 Weak<T>，具体来说是 RefCell<Weak<Node>>。现在 Node 结构体定义如下：

use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

节点能够引用其父节点，但不拥有父节点。在代码清单 15-28 中，我们更新 main 以使用新定义，让 leaf 节点有办法引用其父节点 branch。

use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),

}

代码清单 15-29：在内部作用域中创建 branch，并检查强引用和弱引用计数

leaf 创建后，其 Rc<Node> 的强引用计数为 1，弱引用计数为 0。在内部作用域中，我们创建 branch 并将其与 leaf 关联；此时打印计数，branch 中的 Rc<Node> 强引用计数为 1，弱引用计数为 1（因为 leaf.parent 用 Weak<Node> 指向 branch）。打印 leaf 的计数时，会看到强引用计数为 2，因为 branch 现在在 branch.children 中保存了 leaf 的 Rc<Node> 克隆；但弱引用计数仍为 0。

内部作用域结束时，branch 离开作用域，Rc<Node> 的强引用计数降到 0，因此其 Node 被丢弃。来自 leaf.parent 的弱引用计数 1 不影响 Node 是否被丢弃，所以我们不会发生内存泄漏！

如果作用域结束后尝试访问 leaf 的父节点，我们会再次得到 None。程序结束时，leaf 中的 Rc<Node> 强引用计数为 1，弱引用计数为 0，因为变量 leaf 再次成为 Rc<Node> 的唯一引用。

所有管理计数和值丢弃的逻辑都内置在 Rc<T>、Weak<T> 及其 Drop trait 实现中。通过在 Node 定义中指定从子节点到父节点的关系应为 Weak<T> 引用，你可以让父节点指向子节点、子节点也指向父节点，而不会创建引用循环和内存泄漏。

小结

本章介绍了如何使用智能指针，做出与 Rust 默认使用常规引用时不同的保证和权衡。Box<T> 类型具有已知大小，指向堆上分配的数据。Rc<T> 类型记录指向堆上数据的引用数量，使数据可以拥有多个所有者。RefCell<T> 类型通过内部可变性，提供了一个在需要不可变类型但又需要修改其内部值时可用的类型；它还在运行时而不是编译时强制执行借用规则。

我们还讨论了 Deref 和 Drop trait，它们实现了智能指针的许多功能。我们探索了可能导致内存泄漏的引用循环，以及如何使用 Weak<T> 防止它们。
